Goal

The **Verification Log** is no longer a developer debugging screen.

Its purpose is to answer one simple question:

> **"How did ReForge arrive at this answer?"**

The experience should feel polished, trustworthy, and understandable for end users while still showcasing ReForge's self-healing verification pipeline.

Users should never see raw backend variables such as:

* `decision=accept`
* `answer_len=629`
* `query='...'`
* raw JSON payloads
* internal LangGraph state values

Those belong to developers, not users.

---

# Overall Timeline

The Verification Log should tell a simple story consisting of **three stages**.

```
🔍 Finding Relevant Information

↓

✍️ Generating Draft

↓

🛡️ Verifying Response
```

Do **not** expose internal workflow nodes like Routing Decision.

The UI should explain the process, not the implementation.

---

# 8. Technical Details (Collapsible)

Developers may still need access to raw debugging information.

Instead of displaying it by default, move all implementation details into a collapsed section.

```
▼ Technical Details
```

Inside it may contain

* raw JSON
* retry count
* similarity scores
* chunk IDs
* timings
* internal payloads
* LangGraph metadata

This section should remain collapsed by default.

Regular users should never need to open it.

---

# Design Principles

Throughout the Verification Log:

* Never expose backend variable names.
* Never expose raw JSON unless inside **Technical Details**.
* Use human-friendly language instead of implementation terminology.
* Keep the interface clean and confidence-inspiring.
* The Verification Log should feel like a polished product feature, not a debugger.

The final experience should explain **why the answer can be trusted**, rather than **how the code executed**.
